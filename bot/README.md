# Zher Monitoring — Telegram-бот для земельного мониторинга

Zher Monitoring — это Telegram-бот для фиксации и сопровождения проблем, связанных с земельными участками в Казахстане. Пользователь работает с сервисом прямо в Telegram: отправляет геолокацию, фотографию и описание проблемы, проверяет статус заявки и получает инструкции по земельным процедурам.

Бот не заменяет официальные государственные сервисы. Его задача — помочь человеку быстро собрать первичные доказательства, понять следующий шаг и не потеряться между картой, eOtinish, кадастровыми сервисами и внутренним Django API.

## Статус в монорепозитории

Бот находится в `bot/` рядом с сайтом и существующим [Django backend](../backend/). Авторитетный контракт backend: [docs/backend-design.md](../docs/backend-design.md).

В этом PR существующий бот перенесён без подключения к Django. Для текущего комплекта проекта поддерживается запуск только с `DATA_MODE=mock`. Сохранённый API-клиент несовместим с контрактом bundled Django; адаптер отложен. Переключение на `DATA_MODE=api` или изменение `API_BASE_URL` эту несовместимость не устраняет.

Если не указано иначе, пути `src/`, `test/`, `data/` и `.env` ниже отсчитываются от `bot/`, а команды выполняются из этой папки.

## Что умеет бот

- При первом сообщении предлагает `Қазақша` или `Русский`, сохраняет выбор и показывает интерфейс на выбранном языке.
- Принимает сигнал о проблеме с участком: геолокация, фото, описание.
- Сохраняет сигнал локально в `mock`; в старом API-клиенте предусмотрен `POST /api/reports` по несовместимому с bundled Django контракту.
- Показывает номер принятого сигнала только после успешного сохранения в выбранном режиме.
- Сохраняет владельца сигнала и показывает личный кабинет `Мои обращения`: список, статус, фото, место и следующий шаг.
- Проверяет статус демонстрационной заявки; старый API-клиент использует `GET /api/applications/:trackingNumber`.
- Показывает локальный справочник земельных процедур; старый API-клиент использует `GET /api/procedures`.
- Работает в тестовом режиме `mock`, когда backend еще не подключен.
- Регистрирует команды `/start`, `/reports`, `/language` и `/cancel` в Telegram.

## Пользовательские сценарии

### Первый запуск и язык

При первом `/start` или другом сообщении в личном чате бот показывает выбор `Қазақша / Русский`. До выбора языка основные сценарии не запускаются. После выбора открывается главное меню на выбранном языке.

Выбор сохраняется по Telegram ID в `data/user-preferences.json` и действует после перезапуска бота в обоих режимах данных. Повторный `/start` сразу открывает меню. Сменить язык можно кнопкой `Язык / Тіл` или командой `/language`; после подтверждения нового языка текущий незавершённый диалог сбрасывается, сохранённые обращения остаются.

Переведены меню, подсказки отправки сигнала, проверка заявления, кабинет и локальный справочник процедур. Описания пользователей не переводятся. В старом контракте клиента произвольный текст из backend остаётся в исходном виде, если backend не предоставил перевод; для процедур поддерживается `translations.kk` с текстовыми полями, для пояснения заявления `translations.kk.explanation`. Это описание клиента, а не формата ответов bundled Django.

### 1. Сообщить о проблеме

Пользователь нажимает `Сообщить о проблеме`. Бот по шагам просит:

1. Отправить геолокацию участка.
2. Отправить фотографию.
3. Описать, что произошло.

После этого бот создает сигнал. В поддерживаемом режиме `mock` сигнал сохраняется локально как демонстрационная запись. В режиме `api` клиент пытается отправить данные на `API_BASE_URL` по старому контракту; bundled Django эти запросы не обслуживает как совместимую интеграцию.

### 2. Проверить заявку

Пользователь выбирает `Проверить заявление`, вводит номер заявки, например `KZ-2026-042`, и получает статус, пояснение и дату обновления.

### 3. Посмотреть земельные процедуры

Пользователь открывает раздел `Земельные процедуры` и выбирает тему:

- сведения о земельном участке;
- изменение целевого назначения;
- обращение в госорган;
- демо-сигнал в режиме `mock`.

Каждая процедура содержит шаги, срок, примечание, источник и ссылку на официальный сервис.

### 4. Мои обращения

Кнопка `Мои обращения` или команда `/reports` открывает кабинет в личном чате с ботом:

- обращения отсортированы от новых к старым, по 5 на странице;
- карточка содержит номер, статус, дату создания, описание, координаты и следующий шаг;
- можно открыть сохранённое фото, место на карте и обновить статус;
- карточка и фото доступны только владельцу, в том числе при нажатии старых кнопок;
- кнопка `К списку` возвращает на страницу обращения, `Главное меню` возвращает к другим действиям.

В `mock` отправленные сигналы сохраняются в `data/reports.json` с `telegramUserId` и остаются доступны после перезапуска. Старые записи без владельца не удаляются, но в кабинет не попадают: определить их владельца задним числом невозможно. Незавершённые черновики по-прежнему хранятся только в памяти.

Статус демо-сигнала означает сохранение внутри бота, а не регистрацию в госоргане. Кабинет показывает текущий статус; журнал всех изменений статуса пока не ведётся.

## Архитектура

Компонент `bot/` написан на Node.js и использует Telegraf. Сайт и Django backend находятся в других каталогах монорепозитория.

Основные файлы:

- `src/index.js` — точка входа.
- `src/bot.js` — логика Telegram-бота, меню, шаги диалога.
- `src/report-cabinet.js` — список обращений, карточки, фото и навигация кабинета.
- `src/i18n.js` — русские и казахские тексты основных сценариев, даты и сообщения об ошибках.
- `src/user-preferences.js` — постоянное хранение языка пользователя.
- `src/reports.js` — проверка владельца, фильтрация и сортировка обращений.
- `src/api.js` — слой доступа к API или mock-режиму.
- `src/mock-api.js` — локальная имитация backend API.
- `src/procedures.js` — справочник земельных процедур.
- `src/config.js` — чтение переменных окружения.
- `src/startup.js` — настройка профиля Telegram-бота и запуск.
- `test/` — тесты конфигурации, сценариев, mock API и запуска.

## Режимы данных

### `DATA_MODE=mock`

Режим по умолчанию и единственный поддерживаемый режим бота в текущем комплекте проекта. Подходит для разработки и демонстрации без запуска Django; данные не попадают в его БД и на сайт.

В этом режиме:

- сигналы сохраняются локально в `data/reports.json`;
- кабинет показывает сохранённые сигналы текущего пользователя;
- язык пользователя хранится отдельно от обращений в `data/user-preferences.json`;
- доступна тестовая заявка `KZ-2026-042`;
- процедуры берутся из `src/procedures.js`;
- бот явно сообщает, что данные демонстрационные и не отправляются в госорганы.

### `DATA_MODE=api`

Сохранённый режим старого API-клиента, несовместимый с Django из `../backend`. Для запуска с bundled backend пока не поддерживается.

При выборе этого режима клиент:

- пытается отправлять сигналы в `API_BASE_URL` по старому формату;
- запрашивает статусы заявок и процедуры по старым маршрутам;
- показывает ошибки API пользователю понятным сообщением.

Интеграция отложена; адаптер должен следовать [контракту Django](../docs/backend-design.md). Основные несовместимости текущего `src/api.js`:

- Django требует `Authorization: Bearer <BOT_API_KEY>`. Это отдельный секрет, не `BOT_TOKEN`; текущий `src/config.js` его не читает, клиент не отправляет авторизацию. Добавление переменной в `.env` само по себе ничего не подключит.
- Для `POST /api/reports` нужен `Idempotency-Key` (UUID на обращение, сохраняемый для повторов). Тело использует snake_case и вложенные поля: `telegram_user_id`, `location: { latitude, longitude }`, `photos: [{ telegram_file_id }]`, `description` и обязательную `category`. Сейчас клиент отправляет плоские `telegramUserId`, `lat`, `lon`, `telegramFileId`, `description`, без категории и ключа идемпотентности. Ответы, включая `tracking_number`, `created_at` и статусы, тоже требуют адаптации.
- Проверка статуса: `GET /api/tracking/{tracking_number}?telegram_user_id=...` вместо `/api/applications/:trackingNumber`, с обязательной проверкой владельца на backend. Для чужого и отсутствующего номера возвращается одинаковый `404`.
- Справочник: `GET /api/instructions` вместо `/api/procedures`; формат инструкций также отличается от старого клиента.
- Для кабинета пока нет endpoint списка обращений, разрешённого сервису бота. Существующий `GET /api/reports` предназначен для инспектора и требует inspector session; его нельзя использовать с bot key или открывать анонимно ради кабинета. Tracking возвращает ограниченные публичные данные и не заменяет список, карточки и фото кабинета.

## Требования

- Node.js 20+
- Telegram Bot Token от BotFather
- Для `mock` запуск Django не требуется; подключение к bundled Django через `api` отложено

## Быстрый запуск

Из корня монорепозитория:

```powershell
cd bot
npm ci
Copy-Item .env.example .env
```

Создавайте `.env` из примера только при первом запуске, не перезаписывайте существующий приватный файл. Заполните `bot/.env` своим Telegram-токеном локально:

```env
BOT_TOKEN=your_bot_token_here
DATA_MODE=mock
API_BASE_URL=http://127.0.0.1:8000/api
```

Запуск из той же папки `bot/`:

```powershell
npm start
```

Команда запускает Telegram polling. Пользовательский интерфейс находится в Telegram, а не в терминале. Для остановки нажмите `Ctrl+C`.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | Токен Telegram-бота от BotFather |
| `DATA_MODE` | `mock` для текущего проекта; `api` оставлен для старого несовместимого клиента |
| `API_BASE_URL` | Адрес старого API-клиента; в `mock` не используется, сам по себе не подключает bundled Django |
| `TELEGRAM_API_ROOT` | Адрес Telegram API, обычно менять не нужно |
| `TELEGRAM_STARTUP_TIMEOUT_MS` | Таймаут настройки Telegram-профиля |
| `TELEGRAM_SETUP_PROFILE` | `false`, если не нужно обновлять имя, описание и команды бота |

Приватные `bot/.env`, `bot/data/reports.json` и `bot/data/user-preferences.json` исключены из Git и не должны публиковаться в GitHub или чатах. Пример `.env.example` содержит только шаблон настроек. Если появятся новые файлы с пользовательскими данными, добавьте их в `.gitignore` до коммита.

Перед будущей миграцией отдельно сделайте приватную резервную копию `bot/.env` и всех `bot/data/*.json`, в том числе `reports.json` и `user-preferences.json`, чтобы не потерять настройки, обращения и выбранные языки. Этот PR переносит исходники и документацию; секреты и runtime-данные не копируются и не мигрируют.

## Старый контракт текущего API-клиента

Ниже сохранены подробные форматы, которые ожидает существующий `src/api.js` и интерфейс бота. Это документация только текущего клиента, несовместимая с bundled Django, а не требования к изменению его API. Авторитетный контракт интеграции находится в [../docs/backend-design.md](../docs/backend-design.md); адаптация клиента отложена.

Старый клиент ожидает ответы API в JSON.

Формат ошибки:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Заявление не найдено"
  }
}
```

### `POST /api/reports`

Создает сигнал о проблеме.

Запрос:

```json
{
  "telegramUserId": "123456789",
  "lat": 43.238949,
  "lon": 76.889709,
  "description": "На участке ведутся земляные работы",
  "telegramFileId": "telegram_file_id"
}
```

Ответ:

```json
{
  "id": "REP-2026-001",
  "status": "signal_received",
  "createdAt": "2026-09-25T00:00:00.000Z"
}
```

`telegramUserId` обязателен: бот берёт его из `ctx.from.id`, а не из текста сообщения, и передаёт строкой с положительным целым числом.

### `GET /api/reports?telegramUserId=123456789`

Возвращает все сигналы конкретного пользователя. Поддерживаются массив записей или объект `{ "reports": [...] }`. В текущей версии страницы формирует бот; backend не должен молча обрезать ответ до первой страницы.

```json
{
  "reports": [
    {
      "id": "REP-2026-001",
      "telegramUserId": "123456789",
      "status": "under_review",
      "createdAt": "2026-09-25T00:00:00.000Z",
      "updatedAt": "2026-09-25T06:00:00.000Z",
      "description": "На участке ведутся земляные работы",
      "lat": 43.238949,
      "lon": 76.889709,
      "telegramFileId": "telegram_file_id",
      "explanation": "Материалы рассматриваются",
      "nextStep": "Сохраните дополнительные материалы по проблеме"
    }
  ]
}
```

`id` должен быть уникальным и содержать от 1 до 40 латинских букв, цифр, дефисов или подчёркиваний. `telegramUserId` возвращается для каждой записи; записи без владельца или с другим владельцем бот не показывает. `updatedAt`, `explanation` и `nextStep` необязательны. Даты показываются по времени Казахстана. Без фото или корректных координат соответствующие кнопки не появляются.

Статусы сигналов: `signal_received`, `under_review`, `inspection_scheduled`, `approved`, `rejected`. Для неизвестного статуса бот предлагает уточнить его позже. При `demoOnly: true` карточка всегда указывает, что сигнал сохранён только в боте.

Каждое открытие карточки, фото или обновление повторно загружает список владельца. Для безопасного обслуживания такого клиента сервер должен сам фильтровать записи по владельцу и разрешать доступ только авторизованному сервису бота. Один параметр `telegramUserId` не является авторизацией; дополнительная фильтрация в боте не защищает открытый HTTP API. Текущий клиент авторизацию не отправляет. В bundled Django авторизация уже реализована, но bot-authorized endpoint такого списка отсутствует; inspector `GET /api/reports` нельзя использовать как замену или открывать анонимно.

### `GET /api/applications/:trackingNumber`

Возвращает статус заявления.

Ответ:

```json
{
  "trackingNumber": "KZ-2026-042",
  "stage": "under_review",
  "explanation": "Заявление находится на рассмотрении",
  "updatedAt": "2026-09-25T00:00:00.000Z"
}
```

Поддерживаемые статусы в интерфейсе:

- `under_review` — на рассмотрении;
- `inspection_scheduled` — назначена проверка;
- `approved` — одобрено;
- `rejected` — отклонено.

### `GET /api/procedures`

Возвращает список процедур.

Ответ может быть массивом или объектом:

```json
{
  "procedures": [
    {
      "id": "land-complaint",
      "title": "Сообщение о проблеме с участком",
      "menuLabel": "Обращение в госорган",
      "steps": ["Откройте eOtinish", "Опишите проблему"],
      "durationText": "Срок зависит от процедуры",
      "note": "Официальное обращение нужно отправить через eOtinish",
      "officialUrl": "https://eotinish.kz/ru",
      "officialButton": "Открыть eOtinish",
      "sourceUrl": "https://eotinish.kz/ru",
      "sourceCheckedAt": "2026-09-25",
      "referenceOnly": true
    }
  ]
}
```

## Что важно улучшить дальше

Сейчас реализован первый этап бота: личный кабинет обращений в `mock`. Подключение к bundled Django отложено и требует устранить перечисленные несовместимости. Ниже сохранены продуктовые направления развития бота, а не объём текущего PR.

Приоритетные улучшения:

1. Личный кабинет обращений: реализован список, текущие статусы, карточка, фото и место.
2. Умная категоризация проблемы: определить тип ситуации, уточнить недостающие факты и проверить полноту данных.
3. Черновик официального обращения для eOtinish на основе данных пользователя.
4. Напоминания по срокам: когда проверить статус и вернуться к обращению.
5. Админ-карта и антидубли: находить похожие сигналы рядом и анализировать проблемные зоны.

Главная продуктовая цель: бот должен не просто принять жалобу, а помочь человеку пройти путь от фиксации проблемы до понятного результата.
