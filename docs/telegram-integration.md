# Telegram → Django → сайт

Актуальный бот из ветки `master` (исходный коммит `53a7e5a`) находится в `bot/`. Его адаптер использует тот же Django, что и сайт. Ветка `feat/telegram-bot` содержит более ранний вариант.

## Что появляется на сайте

После отправки пользователем геолокации, фотографии и описания бот создаёт обращение. Карта и список в авторизованной панели обновляются каждые 5 секунд, пока вкладка видима. В карточке отображаются описание, фото и блок «Ответ Telegram-бота»: предварительная категория, рекомендуемый адресат, срочность, проверка геолокации, список доказательств, следующий шаг и раскрываемые черновики текстов.

Анализ сохраняется атомарно с обращением в `bot_result`. Он является рекомендацией бота; проверенный статус обращения меняет инспектор. Тексты паспорта в исходной версии бота формируются на русском; переключение языка сайта переводит подписи интерфейса, а не исходный текст. Приватный ИИ-чат и отдельные спутниковые дела автоматически на сайт не передаются. Новое поле необязательно: старые обращения продолжают работать.

## Настройка

1. В корневом `.env` Django задайте отдельный случайный `BOT_API_KEY`. Для загрузки фотографий задайте `BOT_TOKEN` того же бота. Секреты не коммитить.
2. Выполните миграции: `python backend/manage.py migrate`. Создайте инспектора, если его ещё нет: `python backend/manage.py create_inspector --username inspector` (пароль вводится отдельно).
3. Для Vite в `frontend/.env` задайте `VITE_DATA_MODE=api` и `VITE_API_BASE_URL=/api`. Перезапустите Vite командой `npm --prefix frontend run dev`, войдите на `/login`.
4. Скопируйте `bot/.env.example` в `bot/.env`. Укажите `DATA_MODE=api`, `API_BASE_URL=http://127.0.0.1:8000/api`, тот же `BOT_API_KEY` и настоящий `BOT_TOKEN`.
5. Установите зависимости: `npm --prefix bot ci`. Запуск без наблюдения за файлами: `npm --prefix bot run start:once`.

`mock` у бота и `demo` у сайта являются отдельными локальными демонстрациями и не синхронизируются. Старые JSON-обращения бота не импортируются автоматически. Не запускайте второй polling-процесс с токеном уже работающего бота.

Если бот размещён отдельно, `API_BASE_URL` должен указывать на доступный ему HTTPS-адрес Django с `/api`. `localhost` на сервере бота не ведёт на компьютер разработчика. Для существующего развёртывания из `master` переключите исходники на эту интегрированную ветку, рабочую папку на `bot`, команду на `npm run start:once`, режим на `api` и сохраните постоянный каталог `data`. Смена ветки в Git сама по себе не меняет настройки хостинга.

Для общего локального Docker-стенда: `docker compose --profile telegram up --build -d --wait`. Профиль `telegram` запускается только явно; переменные берутся из корневого `.env`, бот обращается к `http://api:8000/api`. Данные бота сохраняются в `bot_data`. Django допускает внутренний Host `api`. Эта команда запускает настоящий Telegram polling и требует токен.

## Контракт для разработчика бота

- `POST /api/reports`: `Authorization: Bearer <BOT_API_KEY>`, `Idempotency-Key: UUID`; `telegram_user_id` (строка), `location`, `photos`, `description`, `category`, необязательный `bot_result`.
- `bot_result`: `language`, `location_summary`, `land_case_id`, `case_passport`. Поля паспорта: `type`, `typeLabel`, `responsibleAuthority`, `urgency`, `evidenceChecklist`, `officialDraft`, `followUpDraft`, `inactivityComplaintDraft`, `publicText`, `socialText`, `nextAction`, `followUpDays`. Неизвестные поля и превышение лимитов отклоняются.
- `GET /api/bot/reports?telegram_user_id=…`: только bot key, постраничный список обращений указанного владельца. В нём есть паспорт и `telegram_file_id` для кабинета бота. Обычный `GET /api/reports` остаётся только для инспектора.
- `GET /api/tracking/{number}?telegram_user_id=…`: статус своего обращения/заявления.
- `GET /api/instructions`: инструкции.

Сайт читает `bot_result` только из защищённого `GET /api/reports/{id}`. ID Telegram и исходные file_id не добавляются в ответ инспекторского API. Вся интеграция выполняется сервер → сервер, ключ не передаётся React.

Адаптер переводит camelCase из диалога бота в контракт Django, добавляет авторизацию и ключ идемпотентности. После сетевой ошибки повторно используется исходное тело и ключ. Ошибка валидации 400 позволяет исправить описание. Незавершённые черновики диалога хранятся в памяти и теряются при перезапуске; сохранённые обращения находятся в Django. Повторное сообщение с новым ключом после перезапуска является новым обращением.

## Проверка

`npm --prefix bot test`, `npm --prefix frontend test`, `python backend/manage.py test monitoring.tests`.

`python scripts/test-bot-to-web.py --help` описывает сквозную проверку. Она запускает отдельные Django и Vite, создаёт временную базу, вызывает настоящий адаптер бота и проверяет результат в браузере. Telegram/OpenAI не вызываются; фотографии подставлены. Для подтверждения живой доставки отправьте обращение уже настроенному боту и сравните номер в его ответе и на сайте.
